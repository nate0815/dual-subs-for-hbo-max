## 1. 目的與驗證對象

要驗證什麼、不驗證什麼，**以 [DESIGN.md](DESIGN.md)「設計目標」為準**（假設 H1～H4 與判定方式都在那裡），這裡不複製。

一句話：這是個人自用工具，目的是把官方英文 CC 與官方繁中字幕同時放上畫面，拿來練英文。「做得出來」已在偵察階段證實，剩下要驗證的是**全螢幕與換集後還能不能用**。

## 2. 技術方向結論

| 項目 | 選擇 | 一句話理由 |
|---|---|---|
| 形式 | Chrome 擴充功能（Manifest V3），載入未封裝項目 | 自用，不需要上架 |
| 注入方式 | 內容腳本，`world: "MAIN"`，`document_start` | 要在頁面自己的世界裡讀資源請求與 `fetch`；不需要任何權限宣告 |
| 字幕來源 | 讀 DASH 清單檔（`.mpd`），自己抓兩份 `.vtt` | 見下一章「核心判斷」 |
| 解析方式 | 純字串／正規表示式，不用 DOMParser | 清單檔結構實測固定；少一層依賴，也能在 Node 底下直接跑測試 |
| 語言 | 純 JavaScript，不用 TypeScript、不用打包工具 | 規模約 400 行；改了存檔、到擴充功能頁按重新載入就生效 |
| 測試 | Node 內建 `node --test` | 零依賴；解析邏輯是純函式，容易測 |
| 設定 | `localStorage` ＋ 快捷鍵，沒有設定頁 | 先驗證核心，UI 以後再說 |

## 3. 核心判斷 ⭐

**從 DASH 清單檔取得字幕網址，而不是攔截播放器發出的字幕請求。**

- **為什麼這樣判**：HBO Max 的播放器一次只載入使用者目前選的那一條字幕。如果靠攔截，永遠只拿得到一條，做不出雙字幕。清單檔卻列出**所有**文字軌，每條都有 `SegmentTemplate`，可以自己組出網址、自己抓。
- **實測依據（2026-11-11，Adventure Time 第 1 季第 19 集）**：清單檔裡有英文（`en-US`、角色 `caption`）與繁中（`zh-Hant-TW`、角色 `subtitle`）兩個文字軌；兩份 `.vtt` 與清單檔同主機，用頁面內的 `fetch` 回 200，不必帶額外標頭。
- **如果判斷錯了**：例如 HBO 改成用簽名網址、只對播放器放行，那麼自己抓會失敗。退路是回頭用「攔截」，使用者需要先把兩種字幕各切換一次，讓播放器各載入過一遍，再把攔到的內容記起來。體驗差很多，但仍可做。
- **一個沒查清楚的觀察**：偵察時，網路工具看得到英文軌的請求，頁面的 `performance` 資源清單卻找不到它。**原因是猜測，沒有證實**（可能是追蹤範圍不同，也可能是請求走的路徑不同）。這也是不依賴「攔截」的另一個理由。

## 4. 架構

四個檔案，**單向依賴**，載入順序就是依賴順序（`manifest.json` 的 `js` 陣列）：

```
vtt.js  →  mpd.js  →  overlay.js  →  main.js
（純函式）  （純函式）  （操作 DOM）   （把前三者接起來）
```

- `vtt.js`、`mpd.js` 是**純函式**，不碰 `window`／`document`，所以能在 Node 底下直接測。這是刻意切的：最容易因為 HBO 改版而壞的是解析，把它隔離出來，壞了只需要補一份測試與一個小改動。
- `overlay.js` 只負責畫，不知道字幕從哪來。
- `main.js` 負責所有「碰外界」的事：觀察請求、`fetch`、計時器、快捷鍵、設定。

每個檔案的介面細節在 [TECH.md](TECH.md)「模組契約」。

## 6. 為什麼不用現成擴充功能

| 面向 | 自製（本案） | Immersive Translate 等 | 差在哪 |
|---|---|---|---|
| 第二行字幕來源 | HBO 官方繁中軌 | 機器翻譯 | **這是唯一的理由**：我要的是官方翻譯的用詞，不是另一個機器譯本 |
| 範圍 | 只做 HBO Max 雙字幕 | 通用，功能多 | 本案只需要一件事，自製的範圍小到一個下午能做完 |
| 維護 | 自己維護，HBO 改版就要自己修 | 開發者維護 | 這是自製的代價，已接受 |

| 面向 | 自製（本案） | Language Reactor | 差在哪 |
|---|---|---|---|
| 支援平台 | HBO Max | 官方列出 Netflix、YouTube | 沒有找到它支援 HBO Max 的依據，所以不是候選 |

**尚未查證的備案**：EasyDualSub 宣稱可合併官方字幕軌，很新、用戶少、沒有實測。若自製卡在 H3，先試它再決定要不要繼續投入。

完整的決策理由見 [自製而不用現成擴充功能](decisions/2026-11-11-自製而不用現成擴充功能.md)。

## 9. 風險與應對

| 風險 | 機率 | 影響 | 應對 |
|---|---|---|---|
| HBO 改清單檔結構或網址規則 | 中 | 抓不到字幕 | 解析失敗時 `parseTextTracks` 回傳空陣列、主控台印警告，不會拋例外弄壞頁面；修 `mpd.js` ＋補一份測試 |
| 疊加層在全螢幕被蓋住或位置錯 | 中 | 工具不能用 | 掛載目標已設計成「全螢幕元素優先」；實機若仍不行，改掛到播放器容器 |
| 某些作品的字幕拆成多個分段 | 低 | 只顯示前一段 | 目前只讀第一段並在主控台警告；真的遇到再補 |
| 原生字幕沒關，兩層疊在一起 | 高（人為） | 難讀 | 文件寫明要先關閉；自動隱藏列為待決事項 |
| 服務條款 | 未知 | 帳號風險 | **未評估**，僅限個人使用；列入 [DESIGN.md](DESIGN.md)「待決事項」 |
| 公開上架後被內容方檢舉下架 | 中（若公開上架） | 擴充功能被移除、開發者帳號受影響 | 不公開上架；要分享先用「不公開」或「測試人員」，見 [暫不上架商店](decisions/2026-11-11-暫不上架商店.md) |
| 商店名稱／圖示／截圖被認定暗示與 HBO 有關 | 中（若上架） | 被檢舉、審核退件 | 名稱用中性描述，不用 HBO 字樣當品牌，截圖用自製假畫面，不放劇的畫面 |
| 上架後 HBO 改版，所有使用者同時壞掉 | 中（若上架） | 維護責任落在自己身上 | 上架前先把 H3、H4 驗完、補足解析的容錯與測試；沒穩定前不上架 |
| 商店審核要求隱私權政策與權限說明 | 高（若上架） | 退件、延遲 | 目前零權限宣告；上架前補隱私權政策（聲明不蒐集、不傳送任何資料）與「只讀字幕」的說明 |

## 11. 已排除的技術路線

| 路線 | 為什麼排除 | 什麼條件下會重新考慮 |
|---|---|---|
| 攔截播放器的字幕請求（覆寫 `fetch`／`XMLHttpRequest`） | 只拿得到使用者目前選的那一條；也要改寫頁面的內建函式，風險較高 | 自己抓字幕被 HBO 擋下時，作為退路 |
| 用 `DOMParser` 解析清單檔 | 無法在 Node 測試環境直接用；結構又夠固定，正規表示式夠用 | 清單檔結構變複雜、正規表示式難以維護時 |
| 內容腳本跑在隔離世界（預設） | 讀頁面資源請求與 `fetch` 要走更多管道；目前只驗證過主世界 | 想收窄權限、或 Chrome 改變主世界行為時 |
| 加打包工具（Vite 等）、TypeScript | 約 400 行不值得；每次修改要多一道建置 | 程式超過約 1500 行，或要多人協作時 |
| 做設定頁／彈出視窗 | 先驗證核心；快捷鍵已夠調整 | 常用設定超過三四項，快捷鍵記不住時 |
| 公開上架 Chrome Web Store | 版權、服務條款、商標、維護四項風險未評估，見 [暫不上架商店](decisions/2026-11-11-暫不上架商店.md) | H3、H4 驗完、服務條款評估過、確定有人要用；先試「不公開」 |
| 把字幕做成可下載／可查字典 | 超出本專案範圍（見 [DESIGN.md](DESIGN.md)「明確不驗證什麼」） | 另開專案 |
